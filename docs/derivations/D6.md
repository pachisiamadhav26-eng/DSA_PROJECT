# D6 - Cost models for leaderboard operations

Author: Sumit, Analyst. Revised 17 November 2026 before the formal benchmark run. Earlier practice and development measurements are recorded separately in the work log.

## 1. Definitions and implementation versions

Let n be the number of active players, U the number of score coordinates supplied to Fenwick, and h the AVL height. For two input boards, use n1, n2, U1, U2 and heights h1, h2. Let N = n1 + n2. Let t be the number of IDs in a tied-score bucket. U includes prepared coordinates that are currently empty.

This model follows Architect a4dc438, AVL 03f3f57, Fenwick 0d5ad68 and Oracle 6a25781. The benchmark records full commit hashes at build time. If an implementation changes, review this model before measuring that version.

The common order is decreasing score, then increasing player ID. Competition rank is 1 plus the number of strictly higher scores. Select returns the player at a one-based position, so two tied players can share a rank while occupying different positions.

We measure core rank with the score already available. Application parsing, player lookup, input generation, correctness checks and printing are outside the query timer. Loop and checksum work are inside the timed batch. This is mean time per call in a batch, not a measurement of individual-query tail latency.

## 2. AVL rank and select

An AVL node stores its height and subtree size. A minimum-node AVL of height h satisfies M(0) = 0, M(1) = 1 and M(h) = 1 + M(h-1) + M(h-2). This grows exponentially with h, so the height is O(log(n+1)).

For rank, if the current score exceeds the queried score, every player in the left subtree and the current player has a strictly higher score. Add left_size + 1 and continue right. Otherwise continue left. This follows one downward path with constant work per visited node. Add one to the final count for competition rank.

For select(k), the current node's position within its subtree is left_size + 1. Return it if that equals k. Continue left if k is smaller. Otherwise subtract that position and continue right. This also follows one downward path with constant work at each node.

Therefore both operations take O(log(n+1)). If v is the number of visited nodes, useful timing models are `T_rank_A = a0 + a1 * v` and `T_select_A = b0 + b1 * v`. The constants include machine and implementation costs. We do not assign numerical constants before measuring.

## 3. Fenwick rank and select

Fenwick stores descending score coordinates, a count tree, and a sorted ID vector per score. Rank first finds the score boundary by binary search in O(log(U+1)). A prefix sum then counts players at higher scores. Each prefix step clears the lowest set bit of its index, so there are at most O(log(U+1)) steps. Adding the two costs gives O(log(U+1)), followed by the constant-time rank addition.

Select uses binary lifting to find the first score bucket whose cumulative count reaches k. It tests powers of two from large to small, taking O(log(U+1)) steps. The remaining position indexes the sorted ID vector in O(1). Thus full player selection also takes O(log(U+1)). This depends on IDs already being maintained in order.

Let c be coordinate comparisons and f be count-array entries inspected. Models are `T_rank_B = c0 + c1 * c + c2 * f` and `T_select_B = d0 + d1 * f`. Initial power-of-two setup also has logarithmic cost and is absorbed into the select model. Holding U fixed while increasing n leaves these algorithmic bounds unchanged. It does not require measured times to remain exactly constant.

## 4. Score revisions around the queries

An actual revision removes the old key and inserts the new one. AVL performs two logarithmic operations, giving O(log(n+1)) overall. Its membership checks and rotations are included in that bound.

Fenwick updates its counts but also maintains sorted ID vectors. Removing an ID can shift up to t_old IDs, and inserting it can shift up to t_new IDs. The revision cost is O(log(U+1) + t_old + t_new). Tie-heavy workloads can therefore make updates costly even when rank and select remain logarithmic. Revision execution is outside our query timers, but it determines the changing state being queried.

## 5. Split against rebuilding

AVL split follows a search path and rebuilds its two outputs with joins. Using the D1 join result and the D5 height argument, charge each return step to O(1 + delta), where delta is the growth of the output being rebuilt. The output heights grow monotonically and each ends at most at the original height H. The growth charges telescope separately on the two outputs, totaling at most 2H. There are at most H return steps, so the whole split costs O(H) = O(log(n+1)).

Saksham's split copies the prepared coordinates into the outputs, moves ID buckets, and rebuilds the count arrays. It scans the U coordinates a constant number of times, giving O(U+1). Moving a bucket transfers its vector storage rather than copying every player. Allocating output arrays remains part of the public split cost.

Predicted models are `T_split_A = e0 + e1 * log2(n+1)` and `T_split_B = f0 + f1 * U`. The constants hide path, allocation and rebuild costs. The actual experiment prepares input boards before timing and checks the divisions afterwards. Scores equal to the cutoff enter the high division.

## 6. Ordered join, rejoin and general merge

Ordered AVL join receives two correctly ordered trees and a supplied pivot. If their heights differ by at most one, it attaches the pivot above them in constant time. Otherwise it descends the appropriate spine of the taller tree until the heights match closely enough, then rebalances while returning. Constant work per visited level gives O(abs(h1-h2)+1), as established in D1.

Prince's current avl_join_ordered helper assumes ordering and unique IDs. It performs no boundary scans. Its timed work includes result/pivot allocation and the join itself. The model is `T_join_A = g0 + g1 * (abs(h1-h2)+1)`. Record actual input heights, because equal player counts do not uniquely determine AVL height.

Rejoining the divisions through the public merge_from is a different measurement. Prince's ordered-disjoint path checks boundary nodes, extracts a pivot, and joins. Its total cost is O(log(N+1)). The benchmark includes all this public-method work. The supplied-pivot experiment excludes pivot preparation.

For overlapping league ranges, Prince's current implementation collects two sorted node sequences, merges them and builds a balanced tree. Under the application's globally unique ID precondition, that path is O(N). It does not sort IDs for conflict checking. We distinguish this general merge from the faster ordered join; the main season comparison measures rejoining separated divisions.

Saksham's current public merge copies all IDs into a temporary vector and sorts them to detect conflicts before mutation. That adds O(N log(N+1)). Combining score coordinates, merging ID buckets and rebuilding counts adds O(U1+U2+N). The resulting bound is O(U1+U2+N log(N+1)). This validation cost is included even when rejoining previously separated divisions.

A suitable public Fenwick merge model is `T_merge_B = j0 + j1 * (U1+U2) + j2 * N + j3 * N * log2(N+1)`. Treating this implementation as only a linear count rebuild would omit its duplicate-ID validation.

## 7. Experiments that test these models

Use n = 1000, 10000, 100000 and 1000000. Compare U = n with U = min(n,1000). The generator supplies the entire configured universe, including coordinates not used initially. Each query experiment performs one million real revisions and one million queries of each kind. It repeats blocks of at most 256 revisions, then that many rank and select queries. The final block can be shorter. This mix is an explicit Analyst choice.

Both backends use identical initial players and random decisions for the recorded seed. Every repetition starts from fresh state. Use at least five repetitions and save every elapsed time and call count. Report mean time per call, sample standard deviation and minimum/maximum spread. No separate cold-cache behavior is claimed.

Split/rejoin experiments vary the requested high-division percentage. Threshold ties can change actual division sizes. Ordered-join experiments vary the input sizes and record their actual heights. Fresh destructive inputs are built outside the timer. Small inputs can be batched; large inputs are kept bounded in memory.

Use the Adversary's rotation-heavy and unequal-height cases in addition to ordinary workloads. Their exact command order is preserved. Trace timing places a timer around each backend call, so it includes per-call clock overhead and is labelled separately from batched query measurements.

## 8. Counters, cache evidence and interpretation

Available owner hooks expose AVL rotations, ordered-join visits and Fenwick ID shifts. Collect these in separate untimed experiments. Generic Board calls do not expose query-node visits. Always-enabled backend counters still contribute overhead to timing builds and must be disclosed.

Cache explanations require profiler output. Record the machine, cache sizes, compiler/options, event, sampling settings, lost-event status and measured phase. Hardware-event samples are not exact miss totals. Cache profiling is a separate execution from ordinary timing.

Big-O predicts growth rather than which structure wins in nanoseconds. Compare the observed curves with the models and use actual counters/profiling to explain differences. The large runs use snapshots and cross-backend checksums, while Om's differential and invariant tests establish additional correctness evidence. Final measured conclusions belong in REPORT.md after the formal runs.
